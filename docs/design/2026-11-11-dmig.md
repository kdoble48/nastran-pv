# DMIG matrices: mass, stiffness and load quantities

Date: 2026-11-11. Status: agreed with the user (scope, mass bookkeeping, autonomy); the rest was
decided while writing this spec.

## Why

A DMIG is a matrix typed into the deck, with rows and columns tied to grid DOFs. Case control
adds it to the model: `K2GG`, `M2GG`, `B2GG` and `K42GG` before constraints, `K2PP`, `M2PP` and
`B2PP` in the larger set with extra points, and `P2G` as a load. The common source is a reduced
component from another run (`EXTSEOUT` / `PARAM,EXTOUT,DMIGPCH`), a punch file of `KAAX`, `MAAX`
and `PAX` that the system deck includes. nastran-pv lists DMIGs in the card report and does
nothing else with them, so the model mass it reports leaves the component out, and nobody can
see whether the reduced matrices are sound.

The user wants numbers, not pictures: the mass, CG and inertia a DMIG adds, whether a stiffness
DMIG is free-free or grounded, the resultant of a load DMIG, and the natural frequencies of a
stiffness/mass pair. Views on the model (grid glyphs, coupling lines, sparsity plots) are out of
scope.

## The format

- Header: `DMIG, NAME, 0, IFO, TIN, TOUT, POLAR, , NCOL`. IFO 1 square, 2 or 9 rectangular,
  6 symmetric (one triangle written). TIN 1/2 real, 3/4 complex.
- Columns: `DMIG, NAME, GJ, CJ, , G1, C1, A1, B1, ...`; component 0 is a scalar point (SPOINT,
  EPOINT), which has no location (a Craig-Bampton reduction's modal coordinates).
- Selection and scale: `K2GG = 1.2*KAAX + KBUSH`; `PARAM,CK2`, `CM2`, `CB2` and `CP2` scale the
  `K2GG`, `M2GG`, `B2GG` and `P2G` matrices. A DMIG nothing selects has no effect on the run.
- The DOFs are in each grid's displacement system (CD), not basic.
- `M2GG`/`M2PP` mass is not scaled by `PARAM,WTMASS` (it is entered in solver mass units).

## Goals

1. `src/nastran_pv/matrices.py` reads every real DMIG into a sparse matrix with its row and column
   DOFs, never through pyNastran's dense `get_matrix`. A symmetric (IFO 6) matrix written as one
   triangle is mirrored; if both triangles are written they are used as given.
2. **Use and kind.** A DMIG's use is the case-control key that selects it (`K2GG`, ...) and its
   scale the product of the case-control factor and the matching `PARAM` (`CK2`/`CM2`/`CB2`/`CP2`
   for the GG and P2G keys). A DMIG nothing selects gets its kind from its first letter (K
   stiffness, M mass, B damping, P load, as `EXTSEOUT` names them; `K4...` is structural damping),
   or "other". Every subcase is scanned; the first subcase that selects a matrix gives its scale,
   and a different scale in a later subcase is a warning.
3. **Rigid-body modes.** For the DOFs of the deck's grids, the six unit rigid-body motions about
   the basic origin, rotated into each grid's CD (cylindrical and spherical evaluated at the
   grid). Scalar points and grids the deck does not have get zero rows; missing grids are a
   warning (a punch file read without its system deck).
4. **Quantities per matrix** (one row of a root table `DMIG_` per DMIG):
   - all: `Name Use Kind Scale Form Rows Cols Entries Grids ScalarPoints MissingGrids`, and for a
     square matrix `Asymmetry` (max |A − Aᵀ| / max |A|), `DiagonalMin`, `DiagonalMax`,
     `NegativeDiagonals`;
   - mass: the rigid-body mass `R = Dᵀ M D` (6×6 about the origin), `MassX/Y/Z` (its translational
     diagonal), `Mass` (their mean), `MassSpread` ((max − min) / max: a reduction that lost mass to
     ground, or a mass matrix with missing rotational coupling, shows up here), `CG` (the mean of
     the two estimates each axis has: x from `R[1,5]/m_y` and `−R[2,4]/m_z`, and so on, as GPWG
     gives them per direction), `Inertia` about the CG (`R[3:,3:] − m (|c|² I − c cᵀ)`, tensor
     components `Ixx Iyy Izz Ixy Iyz Izx`) and `PrincipalInertia`;
   - stiffness (and damping): `RigidEnergyRatio`, per rigid mode `dⱼᵀ K dⱼ / dⱼᵀ diag(K) dⱼ` (0
     free-free, order 0.1 to 1 grounded; scale-free, unlike `‖K d‖`); `FreeFree` (1 when every
     ratio is round-off: below 1e-5 for TIN 1, 1e-8 for TIN 2, as single and double precision keep
     ~7 and 10+ digits; 0 when not; -1 when no DOF moves); `RigidStiffness`, the diagonal of `Dᵀ K D`;
   - load: `Force` and `Moment` about the origin, `Dᵀ p` for the first column (`Columns` gives the
     count; the CLI prints every column).
   The table holds the matrix as written (scale not applied); `Scale` says what the run applies.
5. **Model totals.** Root arrays `DMIGMass` and `DMIGCG` sum the mass DMIGs that `M2GG` or `M2PP`
   select, each times its scale (mass-weighted CG). `ModelMassWithDMIG = ModelMass + DMIGMass /
   WTMASS` and `ModelCGWithDMIG` add them to the model, in `ModelMass`'s input units (nastran-pv
   does not apply WTMASS to element mass; Nastran does not apply it to M2GG). `ModelMass`,
   `ModelCG`, the diff and the run store do not change. The four arrays exist only when a mass DMIG
   is selected.
6. **CLI `nastran-pv dmig DECK`** prints the table, the model totals, the per-column load
   resultants and the five grids with the largest rigid-body residual force of a non-free-free
   stiffness matrix. It also does the eigen work, which `convert` skips (time budget):
   - stiffness: the count of zero eigenvalues (a mode whose `λ / φᵀ diag(K) φ` is below the same
     round-off cutoff: the rigid-body and mechanism modes) and of negative ones; above 2000 DOFs from
     the 20 lowest, so "at least" when all are zero or negative;
   - each stiffness DMIG paired with a mass DMIG whose DOFs are among its own (zero mass on the
     rest; same name after the first letter, `KAAX` and `MAAX`, else the only one that fits): the first `--modes N` (default 10)
     natural frequencies, `sqrt(λ) / 2π` of `K φ = λ M φ`; dense for up to 2000 DOFs, sparse
     shift-invert (`scipy.sparse.linalg.eigsh`) above.
   `--csv FILE` writes the table.
7. **Card report.** DMIG leaves it (it is now used). A complex DMIG (TIN 3/4) gets a card-report
   row `complex matrix` and only the structure columns. `DMIG,UACCEL` and DMI/DMIJ/DMIJI/DMIK/DMIAX
   stay in the report as `matrix input`.
8. **Plugin.** The reader's root field data carries the table and the totals already; the masses
   view's overlay adds a line with `ModelMassWithDMIG` and `ModelCGWithDMIG` when they exist.

## Non-goals

- Drawing DMIGs on the model (glyphs, coupling lines, sparsity plots).
- OP4 and OP2 matrices (they need a USET map to place their rows), DMI/DMIJ/DMIK, complex
  quantities, and `DMIG,UACCEL`.
- DMIG mass in `diff`, the run store or the derived `cg` field.
- Frequencies of the whole model with its DMIGs (that is a Nastran run).

## MFLUID (added 2026-11-11, same PR)

The user asked to handle MFLUID too, for the same purpose: its mass.

**The card.** `MFLUID, SID, CID, ZFS, RHO, ELIST1, ELIST2, PLANE1, PLANE2 / RMAX, FMEXACT`,
selected by Case Control `MFLUID = SID`: an incompressible fluid below the free surface `z = ZFS`
of the rectangular frame CID (none when blank), touching the CQUAD4/CQUADR/CTRIA3/CTRIAR that ELIST1
(one side: the normal's, or the other for a negative ID) and ELIST2 (both sides) list, if they have
a grid below ZFS. PLANE1/PLANE2 make the frame's x-z and y-z planes symmetric (S), antisymmetric (A)
or neither (N); RMAX is the farthest two elements interact. pyNastran 1.4.1 rejects MFLUID and
ELIST but keeps their lines (`model.reject_lines`), so `fluid.py` parses them (`to_fields`).

**Decisions.**
- Virtual mass is a matrix, direction-dependent, so it is not added to `ModelMass` or
  `ModelMassWithDMIG`. Per card, root table `FLUID_`: wetted elements and area, the enclosed fluid
  volume and mass (or the displaced volume of a body), and the 6x6 rigid-body added mass about the
  basic origin (diagonal and full).
- Volume: `V = -Σ (z - ZFS) n_z A` in the MFLUID frame (normals into the fluid): the divergence
  theorem on the field (0, 0, z - ZFS), which the free surface and vertical symmetry planes add
  nothing to. Positive: fluid inside (a tank); negative: a body in the fluid.
- Added mass: a direct boundary-element method, constant potential per element, collocated at
  centroids: `φ/2 - D φ = -G vₙ`, with images (free surface -, S plane +, A plane -), and
  `M = -ρ Σ φ vₙ A`. Near pairs (within 3 panel sizes) are integrated over 64 sub-triangles, a panel
  on itself exactly. A constant-source collocation was tried first and converged too slowly (sphere
  +4.6% and closed box -12% at ~400 elements); the direct method gives -0.2% and -1.8%, and the
  half-sphere with a symmetry plane reproduces half the whole to round-off. `lstsq`: a closed tank's
  Neumann problem fixes φ only up to a constant, which no rigid motion feels.
- Two-sided (ELIST2) sets need doublets: surface and volume only, a warning, no added mass.
- Size: dense N x N. `convert` and the reader solve up to 2000 wetted elements (seconds), `nastran-pv
  mfluid` up to 6000; larger sets get a warning. FMEXACT is read past, not used.
- MFLUID and ELIST leave the card report (`fluid.USED_REJECTS`).

**Tests.** `tests/data/mfluid.bdf` (hand-worked parsing, sides, dry and missing elements, a bar,
volume 4 and mass 4000, a two-sided set), and `tests/fluid_decks.py` meshes against closed forms:
sphere ρ⅔πa³, closed box ρV, open box vertical ρV below ZFS, symmetric and antisymmetric half
spheres equal to half the whole, a free surface in a shifted CID.

## Code review (PR #83)

Fixed: K2PP/M2PP/B2PP selections come from pyNastran as (real, imaginary, name) and crashed the
build; a DMIG header without columns (a null `K4AAX` from EXTSEOUT) and an empty load crashed it; a
symmetric matrix whose terms are split between the triangles is now mirrored per term; an MFLUID
with a missing or non-rectangular CID is a warning, not a failed build; only MFLUID/ELIST lines are
parsed (another rejected card could raise from `to_fields`), and a free-field line is split by hand
(`to_fields` keeps 8 fields of a long CSV line); the CSV splits the 6x6 added mass; the reader
solves MFLUID once per deck (`Deck.cache`, warnings kept); the masses view shows the DMIG line on a
model without concentrated masses; one table of rectangular coordinate types (`deck.RECTANGULAR`).
